      How to write a useful brief

      Your Walkthrough · Describe It, Don't Build It

      You don't need to write a file. Your job is to describe the need precisely enough that an engineer can build it in an afternoon - and to be the person who says whether the result is actually useful.

      1 · Say it out loud

      Use the sentence from Step 0. A real one sounds like this:

      When a customer reports that a statement looks wrong,
I want to see what the system actually did for that account,
so I can tell the customer whether it's a defect or expected behaviour.

      2 · Answer the five questions an engineer will ask

      They'll askYou answer with
      "Where does the answer live today?"The systems you'd open by hand - the ticket, the report, the log.
      "How do you know when it's right?"One past example where you already know the correct answer.
      "What must it never do?"e.g. "never change the ticket", "never show account numbers".
      "Who reads the output?"You, a customer, an auditor - this decides the wording and detail.
      "What does good output look like?"Sketch it. Even a bullet list on paper is enough.

      3 · Insist on the safety line

      Ask for read-only behaviour explicitly, and require human approval before changes. These are instructions only: enforce access with tool restrictions and read-only credentials in the host application.

      4 · Judge the first version honestly

      • Run it on a case where you already know the answer. Did it agree?
      • Did it show you where each fact came from, or just assert things?
      • Was anything confidently wrong? That's the one thing to report back - it usually means the agent was allowed to guess where it should have said "I don't know".
      A good agent tells you what it observed and separately what it concluded. If you can't tell those apart in the output, send it back.

      Guidance for scoping and approval

      Your Walkthrough · Decide, Scope, Then Approve

      You rarely write the agent. You decide whether it should exist, how far it may reach, what it costs to run, and who owns it afterwards.

      1 · Should this be an agent at all?

      Run the request through Step 0 with the requester. Approve when all four hold:

      RepeatedThe task happens at least weekly, by more than one person.
      Evidence-boundThe answer exists in systems we already connect - not in someone's head.
      Decision-linkedSomeone acts on the output. No decision, no agent.
      CheckableThere's a past case where we know the right answer, to test against.

      2 · Scope the reach - least privilege

      Grant an agent only the specific tools it needs. Grant the minimum that answers the question, and remember reach is inherited: if an agent may delegate to a worker, it effectively reaches that worker's systems too.

      • Read-only by default - configure read-only credentials and deny write tools in the host; prose alone does not deny access.
      • Approval is human - use an explicit approval mechanism for material changes; writing a request is not an approval control.
      • Production is special - production builds, databases and infrastructure changes deserve a named owner, not general access.
      • Redaction is a rule, not a hope - define and verify redaction of secrets, tokens and personal data; do not assume automatic filtering.

      3 · Control the cost

      Delegation is the cost lever. A coordinator on a strong model that reads every log itself is the expensive pattern; a coordinator that delegates lookups to cheap, fast workers is not.

      PieceModelWhy
      Narrow lookup workerFast / low-costExtraction and summarising - little judgement needed.
      Coordinator / role agentStrongerHolds the hypothesis and weighs contradictory evidence.

      Model availability, delegation behaviour and cost depend on your host and subscription. Check its current settings and documentation.

      4 · Roll it out and keep it honest

      1. Pilot with the requester on known-answer cases for a week.
      2. Review the output shape - it should use a shared template so reports are comparable.
      3. Share with the team through a reviewed repository, so everyone runs the same vetted version rather than private copies.
      4. Name an owner - agents drift when the systems behind them change.
      5. Retire anything unused after a quarter. A stale agent that sounds confident is worse than none.
      Governance in one line: keep reviewed definitions in version control, with a named owner and a review date, rather than relying on private chat copies.

      How to build and test an agent

      Your Walkthrough · Build, Review, Test

      1. Describe the trigger, the decision and a known-answer test case.
      2. Grant only the tools and delegates the agent needs. Tick MCP only for the tools it must reach; each MCP server and the service behind it decide what each person may do.
      3. State the procedure, boundaries, expected output and what to do when evidence is missing.
      4. Review the generated file, then save it in .github/agents/ in your workspace.
      5. Test a known case, a missing-evidence case and a forbidden-action request before sharing it.
      Instructions are not enforcement. Tool allowlists, read-only credentials and human approvals must be configured in your assistant, in your MCP servers and in the connected services. This site does not install agents, connect to MCP servers or run AI.

        About Agent Lab

        What it is

        Agent Lab helps you turn a task that keeps costing you time into something your AI coding assistant can do for you: GitHub Copilot, Claude Code or OpenAI Codex. It tells you what to build and writes the files in that assistant's format. No AI runs on this page: it asks you questions and fills in tested templates.

        What it can make

        • Prompt: a shortcut for a request you keep retyping.
        • Skill: fixed steps, followed the same way every time.
        • Agent: weighs evidence from several places, then concludes.
        • Subagent: fetches one specific thing for an agent.

        How to use it

        1. Choose your role and your assistant at the top. The examples, the documents and the file formats follow them.
        2. Explore: answer eight short questions about the task, including the tools it involves and which ones the assistant can reach through MCP. You get a recommendation and, for a bigger request, a plan in small pieces.
        3. Create: finish the result. Pick the files to save in your repository, a brief for whoever builds it, or an approval record, then copy or download it.
        4. Setup (optional): describe your role and experience, so your assistant explains things at your level, and install the Mentor.

        Your data

        Your answers stay in this browser tab and are not sent anywhere. The page remembers your role, time in role and assistant only if you tick "Remember on this browser only". The files you download do not report anything back.
